# FBM roles and objectives in FloRA

**Updated:** October 15, 2026. **Status:** bounded direction; no trained FBM or
maintenance runtime is added by this document.

Alice's [full FBM responsibility register](https://github.com/NIne-WIngEd/A.L.I.C.E/blob/1f8a3d9368f8b3a69afc8dd397001fa9fbd8287c/docs/fable-builder/FBM_ROLES_AND_OBJECTIVES.md)
defines FBM-01 through FBM-16. FloRA contributes construction evidence and must
eventually test a small builder's transfer of its qualified personal-judgment
slice. It does not need the whole Alice builder or continuous maintenance to run
its initial behavioral comparison. PE and MFM stay in their own workstreams;
directly personalized Gemma remains the separately built challenger.

The [frozen experiment goal](EXPERIMENT_GOAL.md) already requires the later builder
transfer test. Deferring maintenance does not remove that obligation. A script
can establish reproducibility; a claim of learned FBM competence also needs
evidence that the builder performs the construction task on unseen eligible
inputs. Neither a hand-tuned second host nor a second empty installation qualifies.

### Minimum transferred slice

1. Enroll the new host and scoped subjects; verify source-use permissions and
   selected public/shared artifact eligibility. Keep private identity isolated.
2. Use the actual qualified external PE/MFM construction/runtime interfaces and
   new-host evidence. Preserve separately produced host/relationship/self state
   needed by the case; do not invent learned producers in this infrastructure chat.
3. Assemble authorized evidence, accepted memory, linked goals, native judgment,
   action and independently observed outcome, governed revision and fresh judgment.
4. Preserve the approved physical foundation and relevant correction, revocation,
   restart and traceability contracts. Expose missing evidence or capability.
5. Run the same independently specified behavioral checks for the new host without
   leaking final cases into construction, calibration or repair.

## 3. Optional maintenance experiment

**FL-FBM-07 — future, not a current prerequisite.** Once a capable FBM exists,
test its FBM-12–15 responsibilities on offline copies of preserved failure cases,
unseen defect families and healthy controls. It may diagnose and propose candidate
repairs; it cannot mutate the live experiment or certify its own fixes.

- Compare against the existing diagnosis workflow with matched evidence, tools,
  allowed edits, attempts and declared compute. Test a dedicated specialist only
  when a concrete candidate exists.
- Measure correct localization, independently verified repairs, missed defects,
  false alarms, regressions and total resource cost. Reject the addition if it
  provides no useful improvement.
- Keep evaluation and promotion outside candidate write access. Any later approved
  update requires versioned lineage, affected regressions and actual recovery
  evidence. A model's assertion that it improved the system is not that evidence.
- Run maintenance outside normal serving, with resource isolation and cancellation;
  background work can still contend for compute. Existing semantic records are
  useful inputs, not a complete data-flow monitor.
- Keep FloRA's evaluated implementation and protocol fixed within each comparison.
  An accepted code change starts a new identified experiment generation. Sealed
  behavioral cases stay out of maintenance training and development feedback.

See the [two-option assessment](research/backbone-2026-10-15/FBM_CONTINUING_MAINTENANCE_ASSESSMENT.md).
Continuing maintenance is part of Alice's full FBM direction. A separate handler
model and its use in FloRA remain optional and unqualified.

## 4. Evidence sequence and completion boundary

1. **Mechanics:** verify the bounded connected architecture and actual native
   interfaces. Retained synthetic passes do not supply qualified model behavior.
2. **Real model integration:** admit the external PE/MFM artifacts and execute
   their complete consumer paths. Keep their construction in their own chats.
3. **Behavioral qualification:** pilot, then freeze independent cases, criteria
   and budgets; test backbone contribution (B), the separately built personalized
   Gemma comparison (P), and the required judgment-update attribution/controls.
   Preserve the [current hypothesis](research/backbone-2026-10-15/ALICE_BACKBONE_HYPOTHESIS.md)
   and the frozen goal's evidence requirements.
4. **Builder transfer:** after the slice is qualified, execute FL-FBM-04–06 with
   isolated hosts. Recipe preparation can proceed earlier; transfer success
   cannot be declared before the actual builder and behavioral results exist.
5. **Optional maintenance:** FL-FBM-07 is a separate claim and experiment. It is
   not required to finish step 3 and does not substitute for step 4.

The immediate next build dependency remains the actual external PE/MFM artifacts.
FloRA is not fully complete merely because those interfaces exist: real-model
integration, behavioral comparison and the required builder transfer remain.
Latency optimization stays deferred until the functional/hypothesis work under
the owner's current direction; no earlier arbitrary cutoff is reinstated here.
Synthetic-only results do not establish real-host benefit or full Alice/Fable
capability. This role document neither builds nor qualifies another model.
